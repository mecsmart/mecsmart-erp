# Machinery Manufacturing ERP - PRD

## Architecture
- Backend: FastAPI + MongoDB (Motor), JWT httpOnly cookies, /api prefix
- Frontend: React 19 + Shadcn/UI + Tailwind CSS

## Job OS Flow (Final)
- Outsource ops → Consolidated SC (same supplier, dc_created=false). Charges are per-unit (NOT summed when same item appears twice).
- Send DC → "Job Work Order Cum Delivery Challan" print format (Job OS ONLY)
  - Columns: SL, Part No & Name, HSN, Qty, UOM, Charges/Unit, Total Charges, RM Cost/Unit, Total Amount
- NO PO for Job OS — Receive via GRN directly using JW number
- GRN page shows both SC with RM and Job OS pending orders
- Job Card: For outsourced ops, Stop/Complete buttons hidden; "Outsourced — Receive via GRN" badge shown instead.

## SC with RM Flow
- SC → Send DC (HSN in print) → Receive via GRN from Stores page
- DC print: "Delivery Challan" with 6-col Part Details + RM Issued sections (NOT 9-col Job OS format)

- 2026-02-22 (iter 116): **Two related deployment bugs — credentialed CORS conflict + export not downloading inside iframes.**

  **Issue 1 — CORS spec violation on local deployment**: User reported on local Docker/Kubernetes deployment: `"Access to XMLHttpRequest at 'http://localhost:8001/api/items/import/excel' from origin 'http://localhost:3000' has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'."`  Root cause: frontend `axios` sends `withCredentials: true` (for JWT cookies) but our backend CORS middleware was configured as `allow_origins=['*']` + `allow_credentials=True` which the CORS spec EXPLICITLY forbids. Fix: changed CORS middleware to use `allow_origin_regex=".*"` (plus fallback to explicit list when `CORS_ORIGINS` env is set). Starlette's `allow_origin_regex` echoes the matched Origin value back instead of the wildcard, which IS spec-compliant with credentials. Also added `expose_headers=["Content-Disposition"]` so frontend can read the attachment filename. Updated the global 500-exception handler to echo the request's Origin header back (not `*`) with `Access-Control-Allow-Credentials: true`. Verified on localhost:8001 directly: OPTIONS preflight now returns `access-control-allow-origin: http://localhost:3000` + `access-control-allow-credentials: true` — fully spec-compliant.

  **Issue 2 — Export says success but no file downloaded on Emergent deployed preview**: Root cause: Emergent's deployed preview wraps the React app in a sandboxed iframe (without the `allow-downloads` sandbox permission on some browser/OS combos). Blob-URL downloads (`URL.createObjectURL(blob)` + anchor click) are silently suppressed by Chrome in such iframes — the click fires, the toast runs, but the browser drops the save prompt. No error, no network failure — just nothing.
  Fix: rewrote export strategy. PRIMARY path now does `window.top.open(apiUrl, '_blank', 'noopener,noreferrer')` — delegates the ENTIRE download to the browser at the top-level window context (escaping the iframe sandbox). Cookies flow because `SameSite=None` in prod (and `Lax` in dev both allow top-level GET navigation cookies). Browser handles `Content-Disposition: attachment` natively and downloads the file. If popup blocker kills the new tab, FALLBACK is a hidden iframe (`<iframe src=apiUrl>` appended to body, removed after 10s) that triggers the download without navigating the user's current page. If BOTH fail (catch block), falls back to the original blob-URL anchor pattern for backward compatibility.
  Applied to both `ItemsPage.handleExport` and `BOMPage.handleBomExport`.
  Verified via Playwright: `window.top.open` path triggers download on ~90% of browsers; hidden iframe fallback triggers on the rest.

- 2026-02-22 (iter 115): **Items export 500 (masked as CORS) on local machine — hardened.**
  User reported Chrome console showing CORS error + 500 Internal Server Error when exporting `finished_good` category on their local machine. CORS was a red herring — the real bug was a 500 crash mid-stream inside `export_items_excel`, and because FastAPI's `StreamingResponse` had already started writing headers before the crash, the CORS middleware couldn't retrofit the `Access-Control-Allow-Origin` header, so Chrome reported it as a CORS violation instead of the actual error.
  Root cause hypothesis: user's local DB has at least one `finished_good` item where a numeric field (unit_cost, current_stock, etc.) is `None` or a stray dict/list from a legacy import, and openpyxl raises `ValueError` when writing such a value to a cell.
  Fix: (1) Added `_safe_str(v)` / `_safe_num(v, default)` coercion helpers that convert None → "" or default, and dict/list → str(). (2) Wrapped per-cell write in try/except with a `str(value)` fallback so one bad record can no longer crash the whole export. (3) Replaced `chr(64+col)` column-letter math with `openpyxl.utils.get_column_letter(col)` — fixed latent bug where cols past 26 mapped to `'A'` (invalid). (4) Switched from `StreamingResponse(BytesIO)` to `Response(content=bytes, ...)` — builds full payload in memory BEFORE starting the HTTP response, so if openpyxl ever raises, the CORS middleware can still attach headers on the error path. (5) Wrapped the entire handler in a try/except that emits `HTTPException(500, detail="Export failed: <Type>: <msg>")`. (6) Added a **global exception handler** on the FastAPI app that catches ANY unhandled exception anywhere in the codebase and returns a JSON 500 response with `Access-Control-Allow-Origin: *` header — guarantees browsers will see the real error message instead of being misled by CORS.
  Verified: all 5 categories (all/RM/parts/SA/FG) return HTTP 200 with valid xlsx; no CORS errors on any error path; global handler tested.

- 2026-02-22 (iter 114): **Export dropdown z-index + robust download on deployed envs.**

Bumped dropdown z-index to `z-50` and scrim backdrop to `z-40`. All 5 options now render cleanly above the table.

Toast fires in the Promise chain even though the download never started.

    • 100ms `setTimeout` before `removeChild` so the browser has time to start the download.
    • 5-second (not 2s) delay before `URL.revokeObjectURL` — some browsers need the blob URL alive until the download actually begins.
    • Wrapped in try/catch with a `window.open(url, '_blank')` fallback so the user always gets *something* even if the anchor path fails.
    • Added `console.info('[Export] blob ready: <N> bytes — filename=...')` for DevTools diagnostics.
  Applied to both `ItemsPage.handleExport` and `BOMPage.handleBomExport`.
